# Make OKF profiles self-documenting

This MasterPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Vision & Scope

Today a profile can say what it demands and, since [ADR 4](../adr/4-self-documenting-profiles.md),
say a little about why in optional `description` prose. But that prose is only ever
seen by someone who runs `okf profile show` and reads a flat, machine-shaped dump, or
who opens the Dhall descriptor and reads it by hand. A team that adopts a profile has
no way to publish it as something a human browses, links to, or reviews in a pull
request.

After this initiative, any OKF profile can emit an OKF bundle that documents itself.
The command is `okf profile document`, a third subcommand beside the existing
`okf profile list` and `okf profile show`. Given a registry export or a plain Dhall
descriptor file, it writes a small bundle: one concept for the profile as a whole and
one concept per declared `type` rule, cross-linked with bundle-absolute Markdown links,
plus the `index.md` files that `okf index` already knows how to generate. Because the
output is an ordinary OKF bundle, every tool okf already ships works on it —
`okf validate`, `okf graph`, `okf show`, `okf index` — and so does any downstream OKF
consumer such as Mori.

The shape of the output, using a profile named `acme` with two type rules:

```text
acme-profile/
  index.md              generated by Okf.Index
  profile.md            type: OKF Profile
  types/adr.md          type: OKF Profile Type
  types/incident.md     type: OKF Profile Type
```

Each type concept renders the *effective* rules for that type — the merge of the
profile-wide frontmatter rules and that type rule's own, exactly as
[ADR 5](../adr/5-compile-profile-rules-before-validation.md) defines the merge — so a
reader learns what actually applies to a concept of that type rather than having to
compose two declaration sites in their head.

What someone can do after this initiative that they cannot do today: point
`okf profile document` at the profile their repository validates against, write the
result into `docs/`, commit it, and have a browsable, linkable, reviewable description
of their house conventions that is regenerated from the descriptor rather than
maintained by hand. Running the command twice produces byte-identical output, so it is
safe to wire into CI as a drift check.

In scope: a public inspection API on okf-core's compiled profile; a pure renderer in
okf-core that turns a compiled profile into concepts in memory; the `okf profile
document` CLI subcommand with preview and write modes; a shipped meta-profile that the
generated bundle validates against, proving the loop closes; and user documentation,
an embedded help topic, and changelog entries.

Explicitly out of scope. The generator does not write into an existing bundle that it
does not own, and does not delete files it did not generate; it overwrites exactly the
files it produces and leaves everything else alone. It does not fetch or install
profiles — a registry is still only ever read, per
[ADR 3](../adr/3-profile-registries.md). It does not render HTML, produce a website, or
add any templating engine; the output is Markdown concepts and nothing more. It does
not make `description` prose checkable — descriptions stay documentary only, as
[ADR 4](../adr/4-self-documenting-profiles.md) decided, and this initiative adds no
`ProfileViolation` constructor. It does not add a second binary: the decision to keep
this in the `okf` executable is recorded in the Decision Log below. Shell completion
needs no work at all, because `okf-cli/src/Okf/Cli/Completions.hs` generates scripts
that call the binary back through optparse-applicative's own completion protocol, so a
new subcommand is completed automatically.


## Decomposition Strategy

The initiative was decomposed by functional concern into five work streams that form a
mostly linear chain, because each one produces an artifact the next consumes and each
one is independently verifiable on its own.

The first concern is **reading what a profile actually means**. `Okf.Profile.compileProfile`
already computes the merged, per-type rule set that validation uses, but
`CompiledProfile` is opaque and `EffectiveFieldRule` is private. A documentation
generator that recomputed the profile/type merge outside the compiler would duplicate
every merge rule ADR 5 defines — vocabulary intersection, cardinality agreement, format
narrowing, accumulated presence clauses, nested rules — and would drift the first time
one of those rules changed. So exposing a read-only view of the compiled rules is its
own plan and the foundation for everything else.

The second concern is **turning a compiled profile into concepts**. This is pure, total,
deterministic computation with no IO: a profile in, a list of `Okf.Bundle.Concept` out.
Keeping it in okf-core rather than the CLI follows the precedent ADR 3 set when it put
registry enumeration in okf-core — "a future consumer that wants to attach a registry
profile to a registered bundle reuses the library rather than shelling out to `okf`" —
and Mori already consumes okf-core's profile machinery directly. It is verifiable
entirely in the okf-core test suite: the produced concepts must serialize, re-parse to
the same value, validate cleanly under `validateBundle StrictAuthoring`, have no
dangling references, and be byte-identical when rendered twice.

The third concern is **the command-line surface**. Option parsing, resolving where the
profile comes from, preview versus write, directory creation, index generation, and the
overwrite and idempotence rules that ADR 3 explicitly deferred when it said "a writing
command would need its own overwrite and idempotence rules and is deferred". That
deferral is what this plan lifts, so it carries the ADR change.

The fourth concern is **proving the loop closes**. A profile that documents itself is
only convincing if the documentation it produces is itself a valid, profile-conformant
OKF bundle. Shipping a meta-profile — a profile describing profile-documentation
bundles — and validating generated output against it under `--profile-enforce --strict`
turns the claim into a test. This is separable from the generator because it consumes
the generator's published contract rather than its internals.

The fifth concern is **telling users it exists**: `docs/user/profiles.md`,
`docs/user/cli.md`, the embedded `okf help profiles` topic, and the changelog. The
repository already treats CLI surfacing and user documentation as a distinct stream —
see `docs/plans/9-surface-okf-authoring-in-the-cli-and-user-docs.md` — and separating it
keeps the generator plans focused on behavior rather than prose.

Alternatives considered and rejected. A **single self-contained concept file** per
profile was considered: simpler to produce and to paste anywhere, but it yields no
graph, no per-type addressability, and one very large document for a profile with many
types; the bundle shape is what makes `okf graph` and `okf show` useful on the output.
A **separate `okf-doc` binary** was considered because the user raised it: it was
rejected because it would duplicate registry resolution, configuration loading, error
rendering, and completion generation, and would split the `okf profile` command family
across two tools for no gain; okf ships exactly one executable today, and `okf-kit` is a
content repository rather than a second CLI. **Merging the CLI plan and the documentation
plan** was considered and rejected because the docs are worth writing against a settled
command surface, and separating them lets the command land and be exercised first.
**Merging the meta-profile plan into the generator plan** was rejected because the
meta-profile is a consumer of the generator's output contract; keeping it separate is
what forces that contract to be written down rather than assumed.

Relevant ADRs consulted, by repository-relative path:

[ADR 1](../adr/1-profile-declared-document-ids.md) establishes that profiles are
advisory and that a bundle deviating from a profile is still OKF-conformant. It also
defines profile-declared document IDs (`idField` on the profile, `idPrefix` on each type
rule) and document-reference rules, all of which the generated documentation must render
faithfully.

[ADR 3](../adr/3-profile-registries.md) defines a registry as any Dhall expression
evaluating to a record of profile values, puts enumeration in okf-core rather than the
CLI, keeps the okf → okf-profiles dependency one-way, and pins the default registry by
tag *and* sha256 hash. Crucially for this initiative, it records the deliberate
exclusion: "There is no command that installs or vendors a profile into a project… A
writing command would need its own overwrite and idempotence rules and is deferred."
This initiative lifts that deferral for documentation output specifically and must
amend the ADR.

[ADR 4](../adr/4-self-documenting-profiles.md) is the direct antecedent. It added
optional `description` prose at three levels — the profile, each frontmatter key, each
type rule — and decided that descriptions are purely documentary, adding no
`ProfileViolation` constructor and no way for a bundle to fail. It also established the
frozen-legacy-decoder pattern for additive schema changes. This initiative is the payoff
for that prose: it gives the descriptions a destination beyond `okf profile show`.
Nothing here makes them checkable.

[ADR 5](../adr/5-compile-profile-rules-before-validation.md) is the reason plan EP-1
exists. It keeps `ProfileSpec` as the raw, public, order-preserving descriptor and
introduces an opaque `CompiledProfile` holding the merged effective rules, with rules
for merging vocabularies (intersection), cardinality (matching explicit declarations),
formats (equal, or `Uri` narrowed by `UriWithScheme`), presence (accumulated ordered
clauses), nested one-level records, references, and the third `optional` presence class.
Documentation must render the compiled view, not the raw one, or it will lie about what
applies to a given type.

[ADR 2](../adr/2-interactive-bundle-and-concept-selection.md) was scanned and is only
tangentially relevant: it establishes that `okf profile list` and `okf profile show` are
read-only and behave identically with or without a terminal. `okf profile document` in
preview mode must keep that property; only `--write` touches the filesystem.

## Dependency Graph

The chain is EP-33 → EP-34 → EP-35 → EP-36 → EP-37, with one place where parallel work
is possible.

EP-34 hard-depends on EP-33 because the renderer's whole job is to display the effective
per-type rules, and those live behind `CompiledProfile`'s opaque wall until EP-33 opens a
read-only window onto them. Without EP-33 the renderer would either not compile (the
types are not exported from `Okf.Profile`) or would have to re-derive the merge, which
the Decomposition Strategy above rejects.

EP-35 hard-depends on EP-34 because the command's implementation is a thin wrapper: it
resolves where the profile comes from, calls `renderProfileDocumentation`, and either
prints or writes the resulting concepts. There is nothing to print or write until the
renderer exists.

EP-36 hard-depends on EP-35 because the end-to-end proof it adds runs the actual command
against the shipped `docs/profiles/postgresql.dhall` descriptor and validates the result.
It soft-depends on EP-34 in the sense that the meta-profile encodes the frontmatter
contract EP-34 defines; the descriptor could be drafted in parallel with EP-35 once EP-34
has landed, but it cannot be *verified* until the command exists.

EP-37 hard-depends on EP-35 because user documentation must describe a settled command
surface — the exact flags, the exact preview output, the exact exit behavior. It
soft-depends on EP-36 because the meta-profile is worth mentioning in the docs as the
recommended way to check generated output in CI; if EP-36 slips, EP-37 can ship without
that paragraph and add it later.

Parallelism. EP-36 and EP-37 can proceed concurrently once EP-35 is Complete, provided
whoever writes EP-37's prose does not describe the meta-profile until EP-36 settles its
name and location (`docs/profiles/profile-documentation.dhall`). Everything before that
point is strictly serial.


## Integration Points

**The compiled-rule inspection API.** Defined by EP-33 in
`okf-core/src/Okf/Profile.hs` and consumed by EP-34. The shared artifact is a read-only
view of a compiled profile: the list of declared type names, the profile-scope effective
rules, the effective rules for a named type, and accessor functions on
`EffectiveFieldRule` for presence clauses, description, allowed values, cardinality,
format, reference rule, and nested element fields. EP-33 owns the exact names and
signatures and must not export the `EffectiveFieldRule` constructor, so the internal
encoding stays free to change; EP-34 consumes only the accessors. This is an additive
export change, so Mori's `mori-cli/src/Mori/Okf/Advisory.hs` — which exhaustively matches
`ProfileViolation` and `ProfileDefinitionError` per ADR 5 — is unaffected and needs no
coordinated release.

**The generated bundle contract.** Defined by EP-34 and consumed by EP-35, EP-36, and
EP-37. The shared artifact is the exact shape of the output: the concept IDs
(`profile` and `types/<slug>`), the frontmatter `type` strings (`OKF Profile` and
`OKF Profile Type`), which frontmatter keys each concept carries, and the slugging rule
that turns a free-text profile `type` string such as `BigQuery Table` into a valid
concept-ID segment. EP-34 must write this contract down explicitly in its plan and in
module documentation, because EP-36's meta-profile encodes the same contract in Dhall
and the two disagreeing is exactly the silent conflict this section exists to prevent.
Any change to a `type` string or a required frontmatter key after EP-36 lands must
update the meta-profile in the same change.

**The `Okf.Profile.Documentation` module surface.** Defined by EP-34 and consumed by
EP-35. The shared artifact is the module name, the options record that controls output
(root concept ID, type concept directory, an optional caller-supplied timestamp), and
the top-level entry point `renderProfileDocumentation`. EP-34 owns it. EP-35 must not
add rendering logic of its own; anything the CLI wants rendered belongs in the module so
that Mori and other library consumers get it too.

**The `okf profile document` command surface.** Defined by EP-35 and referenced by EP-36
and EP-37. The shared artifact is the subcommand name, its flags, its preview format, and
its exit codes. EP-36 invokes it in a test; EP-37 documents it. EP-35 owns it and must
keep the parser-level tests in `okf-cli/test/Main.hs` alongside the existing
`parseSucceeds` and `parse…Matches` patterns so a later flag rename breaks a test rather
than silently invalidating documentation.

**ADR 3's deferred writing command.** EP-35 owns lifting the exclusion recorded in
[ADR 3](../adr/3-profile-registries.md). It must amend that ADR in the same change rather
than leaving a contradiction in durable project memory, and it must state the overwrite
and idempotence rules ADR 3 said such a command would need.

Cross-plan decisions that should become ADRs. A new ADR is warranted for this initiative
as a whole, covering: that profile documentation is generated as an OKF bundle rather
than a single file or a rendered site; that the generator lives in okf-core rather than
the CLI, extending the ADR 3 precedent; that generation reads compiled effective rules
rather than raw declarations, and why; that generation is deterministic and never reads
the clock implicitly, so output is safe to commit and diff; and that the generated
concept `type` vocabulary is a published contract other tools may key on. EP-35 should
create it (it is the plan where the user-visible behavior lands and where ADR 3 must be
amended anyway), and EP-36 should extend it with whatever the meta-profile settles. ADR 4
should be amended to note that `description` prose now has a machine-consumed
destination, while remaining documentary only.

## Decision Log

- Decision: `okf profile document` is a subcommand of the existing `okf` binary, not a
  new `okf-doc` executable.
  Rationale: the user raised the question explicitly. A second binary would duplicate
  registry reference resolution (`resolveRegistryReference` in
  `okf-cli/src/Okf/Cli.hs`, with its `--registry` → environment → configuration
  precedence), configuration loading, error rendering, and completion script
  generation, and would split the `okf profile` family across two tools. okf ships one
  executable today; `okf-kit` is a content repository of agent skills, not a second CLI.
  Date: 2026-07-31

- Decision: a profile generates an OKF *bundle* — a root profile concept plus one
  concept per declared type rule — rather than a single self-contained concept file.
  Rationale: the point of "self-documenting" is that the documentation is itself an OKF
  artifact, so every tool okf already ships works on it. A bundle gives per-type
  addressability (`okf show acme-profile types/adr`), a real link graph
  (`okf graph`), and generated indexes. A single file would be simpler to produce but
  would degenerate into one very large document for a profile with many types and would
  offer no graph at all.
  Date: 2026-07-31

- Decision: the generator lives in `okf-core`, not in `okf-cli`, and the CLI command is
  a thin wrapper over it.
  Rationale: follows the precedent [ADR 3](../adr/3-profile-registries.md) set for
  registry enumeration — okf-core owns profile machinery so a library consumer such as
  Mori reuses it rather than shelling out to the `okf` binary. It also makes the
  renderer testable as a pure function with no filesystem involved.
  Date: 2026-07-31

- Decision: documentation renders the *compiled* effective rules, which requires
  exposing a read-only inspection API on `CompiledProfile` first (EP-33).
  Rationale: [ADR 5](../adr/5-compile-profile-rules-before-validation.md) defines a
  non-trivial merge between profile-scope and type-scope declarations — vocabulary
  intersection, cardinality agreement, format narrowing, accumulated presence clauses,
  nested rules. Rendering the raw `ProfileSpec` would show two declaration sites and
  leave the reader to compose them; recomputing the merge in the renderer would
  duplicate ADR 5's semantics and drift. Neither is acceptable, so the compiler's own
  answer is exposed.
  Date: 2026-07-31

- Decision: the initiative is decomposed into five child plans in a near-linear chain
  rather than fewer, larger ones.
  Rationale: each of the five produces an artifact the next consumes and each is
  independently verifiable — EP-33 by okf-core unit tests, EP-34 by pure-function tests
  plus bundle validation, EP-35 by CLI parser and filesystem tests, EP-36 by an
  end-to-end self-validation test, EP-37 by inspection. Collapsing EP-33 into EP-34
  would hide a public okf-core API change inside a feature plan; collapsing EP-36 into
  EP-34 would let the output contract stay implicit.
  Date: 2026-07-31

- Decision: shell completion is explicitly out of scope and requires no work.
  Rationale: `okf-cli/src/Okf/Cli/Completions.hs` emits scripts that call the `okf`
  binary back through optparse-applicative's completion protocol
  (`--bash-completion-index`, `--bash-completion-word`,
  `--bash-completion-enriched`), so the binary walks its own parser tree and a new
  subcommand is completed automatically. Recording this so a later contributor does not
  go looking for a completion list to update.
  Date: 2026-07-31

- Decision: generated output must be deterministic and must never read the clock
  implicitly; any `timestamp` frontmatter comes from an explicit caller-supplied value.
  Rationale: the output is meant to be committed and re-generated. If the generator
  stamped the current time, every regeneration would produce a diff and the CI drift
  check that motivates the feature would be impossible.
  Date: 2026-07-31
